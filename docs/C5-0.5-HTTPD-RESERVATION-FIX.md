# C5 0.5.0 — HTTPD reservation fix 2

## Confirmed failure

The user's photo of the failed C5 startup shows:

```text
1528 [ui] UI initialized
1533 [boot] Web API initialization failed: ESP_ERR_HTTPD_TASK (0xb008); internal largest=9216 B
5475 [os] Startup: missing=0x04; UI=3ms; network=250ms; stable=0s/10s; confirm_err=0x0
```

This establishes HTTPD task creation failure after UI initialization. HTTPD asks
for a 16,384-byte internal stack; the reported largest internal allocation is only
9,216 bytes. UI/network heartbeats remain fresh, but the API gate never passes.
There is no CPU-exception evidence in the photo. The first memory fix did not
resolve this physical startup failure.

The user later clarified that power loss was a separate observation, not the
explanation of the automatic startup rollback. As general recovery behavior only,
ESP-IDF's rollback bootloader marks
a previous `PENDING_VERIFY` boot as aborted when it next boots. Power loss or reset
before confirmation therefore also selects the previous valid 0.4 firmware; it
does not wait for the application's 45-second watchdog to expire.

## Change

Paired C5 now starts HTTPD **before UI construction**, after network initialization.
This reserves its original 16 KiB internal stack before LVGL's allocations and
UI/shell task stacks can fragment the heap. The prepared HTTPD instance has **no
routes**. Existing dashboard/API/recovery routes are registered only after UI
initialization succeeds. There is no settings/control API into an uninitialized UI.
Standalone boards retain their existing start timing; S3 still has no local server.

The C5 build also sets `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=0`, so ordinary malloc
prefers available PSRAM even for small objects such as LVGL widgets/styles.
Explicit internal/DMA allocations and FreeRTOS stacks remain internal. Existing
Wi-Fi/LwIP PSRAM preference and the explicit external log history from fix 1 remain.
The 32 KiB internal reservation is unchanged. PSRAM remains required by this board.

No web stack reduction, external task stack, startup-health exception, timeout
extension, new pin, SD format or credential/calibration reset is included. API
health remains unset until routes, UART adapter and paired services initialize.
The other board's presence is not required; C5 can be tested with UART wires removed.

Route startup now has one owner, reuses the prepared server instead of starting a
second instance, and reports the failed URI/error before cleaning up a partial
registration. Ordinary legacy startup still prepares and registers in one call.

## Install

This is system **0.5.0**, C5 build revision `c5-web-startup-fix-2`, compatible with
the installed S3 image. Update **C5 only** through its working fallback's own
numeric-IP dashboard using this revision's `UPLOAD-THIS.bin`. Choose Restart into
update. Leave S3 installed and its native-app issue for a separate task.

Keep C5 powered for at least a minute after restart. Check physical version 0.5.0,
touch, C5 dashboard and `Startup checks passed; firmware confirmed` in Logs. Once
confirmed, a normal power cycle should retain 0.5.0. Do not power-cycle during the
first confirmation window. If it fails, retain the full new error line, since a
later allocation stage can produce the same API health mask.

The image is a browser OTA application, not a USB merged binary. Existing updater
selects the inactive slot automatically. No device was accessed or flashed here.
Physical acceptance of fix 2 is pending.

## Validation

Actual app_main tests verify HTTP task preparation before UI construction, route
activation after UI, then UART/paired-service startup, with API health retained
only when all required stages succeed. The actual new web startup sequencer is
compiled under ASan/UBSan. Its SDK double reproduces the observed 9,216-byte limit:
late HTTPD allocation fails, early reservation succeeds and can register routes
once the remaining heap has fragmented. It checks no routes during preparation,
no duplicate task on activation, exact HTTPD error propagation, route-failure
cleanup, access prerequisite and repeated-registration rejection.

The host model demonstrates allocation order and lifecycle; it is not a measured
physical heap or RF-coexistence run. See the release validation for final build,
regression count, exact image hash and configuration/target ELF checks.
