# C5 0.4.3: Lua library/binding ABI correction

The user installed OS 0.4.2 and Calculator, then reported:

    58172 [com.cydos.calculator] Installed revision
    63385 [com.cydos.calculator] [string "main.lua"]:94: Invalid color

The calculator now reaches Lua entry execution. Line 94 sets the valid RGB color
0x101216. This is distinct from the preceding synchronous ESP_ERR_NO_MEM launch
failure; the error is generated by the native set_background argument check.

Root cause is confirmed in the actual C5 ELF debug types, not inferred only from
host behavior. In 0.4.2 the Lua library's lapi.c has sizeof(lua_Integer)=4, while
app_runtime/runtime.c has sizeof(lua_Integer)=8. components/lua/CMakeLists.txt
privately defined LUA_USE_C89. Lua 5.4.8 then selects C89 long/double numbers in
its library; consumers without that private flag select long long/double. On the
32-bit ESP32-C5, long is 4 bytes and long long is 8. Calls such as luaL_checkinteger
therefore have incompatible return/argument conventions. A valid color can be
read as an out-of-range value. Other integer-valued API calls are affected too.

The previous Linux x86_64 test machine uses 8-byte long and long long, masking
this build-configuration mismatch. Prior successful host UI renders were not
sufficient target ABI validation. They are not evidence of physical acceptance.

Correction:

- Remove the private LUA_USE_C89 override. Use Lua's standard long long/double
  configuration consistently. Export the remaining LUAI_MAXCCALLS=32 option to
  consumers, and mirror this configuration in the native test build.
- Build a guard source into the Lua component asserting 8-byte lua_Integer and
  lua_Number. Add the same compile-time assertions in the app binding component.
- Before runtime initialization, compare library-reported integer/number sizes
  against the binding sizes, refusing a mismatched library rather than running it.
- Keep 0.4.2's PSRAM/worker memory changes, 0.4.1's picker fix, API/permissions,
  partitions/settings and normal settings-preserving C5 OTA behavior.

Validation: 134 regressions pass, no skips. Four new tests use the actual Espressif
RISC-V compiler in RV32/ILP32 mode: the default configuration has 8-byte integers,
the old C89 override demonstrably selects 4-byte integers, the library guard
rejects that old configuration and accepts the corrected configuration.
The finished 0.4.3 C5 ELF independently reports 8-byte lua_Integer in both the Lua
library and app bindings. The actual Lua/LVGL runtime passes ASan/UBSan checks,
including the prior launcher lifecycle tests. Unchanged Calculator 1.0.0 passes
24 arithmetic/error scenarios and all 20 unclipped keys in all four layouts.

This candidate is prepared, not physically installed/confirmed. The installed
calculator revision can be reused after the OS update. This is a C5-only artifact;
carry this Lua build correction into the deferred S3/paired branch before future
app acceptance there. Raw device credentials/private sdkconfig are not imported.
