# C5 0.5.0 — web startup fix 1

The user reports that S3 boots 0.5.0, while C5 boots it, displays
`startup missing: 0x04`, then returns to its prior firmware. The user also
confirmed the preceding `Web API initialization failed` log. Bit 0x04 is API
readiness. This identifies a required web-service startup failure followed by
the existing 45-second startup rollback; it is not evidence of a CPU exception.
The exact HTTPD error code and internal-memory values were not supplied.

Internal RAM pressure is the leading explanation, consistent with the earlier
captured C5 0.4.3c issue. The 0.5 manager adds service stacks and Bluetooth-linked
state. The original 0.5 retained a 20,480-byte log array in internal BSS and left
ESP-IDF's Wi-Fi/LwIP external allocation preference disabled.

## Change

Only the paired C5 runtime moves its same 64 by 320-byte log history into an
explicit PSRAM allocation, before network/UI startup. It fails core initialization
if that allocation fails, rather than reducing logging or consuming internal RAM
as a fallback. Standalone builds and S3 keep their existing placement. The image
also enables `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y` for paired C5 builds. This is
ESP-IDF's supported preference for eligible networking allocations; internal-only
radio/DMA allocations and task stacks retain their required capabilities.

Required HTTPD still starts before UART and paired services. Its 16 KiB stack,
all health gates, ten-second stable window and 45-second rollback remain intact.
Paired startup errors now retain the exact failing UART/service stage and error
code rather than collapsing both to a generic message. No pin, selector,
partition, calibration, credential or SD-data change is included.

This is **0.5.0 with a C5 build revision**, `c5-web-startup-fix-1`. The shared
system version and service schema remain compatible with the installed S3 0.5.0.
Do not update S3 for this fix. Its native-app issue is explicitly deferred.

## Install and acceptance

Use the C5's own numeric dashboard address while it is on its working fallback.
Upload this revision's C5 `UPLOAD-THIS.bin` through that dashboard's System update,
then choose Restart into update. This is an OTA application image, not a merged
USB image. Do not use the paired container through a 0.4 updater.

Success requires the physical C5 to remain on 0.5.0 beyond one minute, touch and
its own dashboard to work, and Logs to show `Startup checks passed; firmware
confirmed`. If it reverts, capture the complete `Web API initialization failed`
line including the error and `internal largest`, or the new paired-stage error.
No device was accessed or flashed during this fix. Physical success is pending.

## Reproduction and evidence

In a clean source checkout, `scripts/build_paired.py` includes and verifies the
new C5 networking setting. The dedicated revision build uses the same qualified
115200-baud TX5/RX4 link and blank initial private fields. The original 0.5 outputs
are preserved separately. See the release validation for final image digests,
actual ELF BSS reduction and regression/build results.

New tests compile the actual paired C5 runtime with ASan/UBSan, reject PSRAM
allocation failure, exercise 64-line wrap and truncation, retain history through
runtime reinitialization and exercise existing launch/failure/relaunch checks.
Actual app_main tests cover web-before-link/service ordering and failure at all
three stages, retaining unconfirmed startup on each failure. Existing platform,
OTA, paired RPC/storage/network/coordinator/UI/browser regressions also run.
Host doubles cannot establish real radio heap usage or physical boot acceptance.
