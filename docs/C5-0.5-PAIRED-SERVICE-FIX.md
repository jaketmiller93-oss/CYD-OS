# C5 0.5.0 — paired-service startup fix 3

The user reports revision 2 now reaches `Paired service initialization failed`.
In actual app_main this follows successful HTTPD setup and UART adapter startup.
The service error code and `internal largest` value were not supplied, so the
exact failing substage is not established. A disconnected S3 is not a cause of
this local initialization failure: startup does not require a live remote peer.
The user clarified that the power-loss observation was separate; do not treat it
as the explanation of this automatic startup rollback.

## Resource correction

C5 still initialized an invisible Apps view and its 8,192-byte `app_folders` task,
even though the paired manager launcher has no Apps entry and app operations go
to S3. This revision omits that view/queue/worker on the C5. S3 and standalone
launchers keep their existing Apps behavior. Resize/open tolerate an absent view.

C5's LVGL draw buffer also occupied 15,360 bytes of internal DMA memory, in
addition to a second DMA rotation buffer. The paired C5 now draws in PSRAM and
copies or rotates into **one retained internal DMA buffer** for every flush.
Unrotated pixels are copied too; SPI never receives the PSRAM draw pointer.
The existing asynchronous color-done callback releases the flush, retaining the
staging buffer until DMA completes. Buffer pixel capacity and transfer dimensions
are unchanged; no smaller strips or external task stacks are introduced.

Together these eliminate 23,552 bytes of internal allocation requests, plus the
unused worker's queue/control overhead. This is an allocation-budget comparison,
not a measured increase in physical free heap. Unrotated rendering gains one
bounded memory copy per flush; rotation already required a copy/transform.

## Accurate failure handling

RPC startup now identifies mutex, request PSRAM, response PSRAM or 8 KiB internal
service-task failure. Manager startup identifies its settings mutex, NVS namespace
or 4 KiB report task and cleans resources when its NVS/task initialization fails.
The exact manager/NVS error is returned through RPC startup to app_main; previously
it was unconditionally changed to `ESP_ERR_NO_MEM`. Existing records are never
cleared to resolve a startup error. No new NVS schema or credential migration.

Revision 2's early HTTPD reservation, delayed routes and PSRAM preference remain.
All required stack sizes, internal/DMA placement, API readiness gates, ten-second
stability and 45-second rollback remain intact. Periodic reports remain required
by the existing initialization path; they are not silently disabled.

## Install and acceptance

System version remains **0.5.0**, C5 revision `c5-paired-startup-fix-3`.
Update C5 only, through its working fallback firmware's own numeric-IP dashboard.
Upload this revision's `UPLOAD-THIS.bin`, then choose Restart into update. Leave
S3 0.5.0 installed; native apps on S3 are deferred. C5 can remain disconnected.

Keep C5 powered for over a minute. Verify physical version, touch/dashboard and
`Startup checks passed; firmware confirmed`. If a new failure occurs, capture both
the new `[pair] Startup failed ...` substage and the `[boot] Paired ... failed`
line with error code/internal block value. If it is an NVS failure, preserve that
actual error rather than assuming additional memory pressure.

This is a browser OTA application, not a merged USB image. No device was accessed
or flashed during preparation. Physical acceptance is pending. Credentials,
calibration, cards, wiring and partition layout are preserved.

## Validation

The actual paired C5/S3 LVGL tests run all four rotations and management/file
flows. They assert no `app_folders` task on C5, its continued presence on S3, draw
buffer capabilities and the exact internal staging pointer passed to C5 flushes.
RPC tests inject mutex, each PSRAM buffer and service-task failure, check cleanup
and preserve a non-memory manager error. Actual manager initialization tests inject
NVS no-space and reports-task failure, check exact errors, diagnostic stages and
cleanup, and ensure no settings writes/erasure during failed startup.

See the release validation for the complete test count, real C5 build, actual ELF
symbol checks, exact hashes and remaining physical acceptance. Host SDK/task/radio
and DMA-completion doubles do not establish physical boot or display performance.
